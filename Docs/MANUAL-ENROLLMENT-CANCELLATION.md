# Ручная проверка POST /enrollments/{id}/cancel

Проверка пункта 3 выполнена 8 ноября 2026: несоответствий явно перечисленным
требованиям не обнаружено. Код приложения при этой проверке не менялся.
`dotnet test FitnessClub.sln --configuration Release --no-restore` —
**257 пройдено, 0 ошибок, 0 пропусков** во всём проекте.

Добавлены 23 сценария: точная граница двух часов и соседние значения, расширенная
матрица возврата, пустой и просроченный абонемент, повтор после начала и отмены
занятия клубом, отсутствие возврата другим клиентам, поздняя отмена с очередью,
FIFO при одинаковом времени постановки и 12 одновременных отмен одной брони.
Также проверяется точный состав успешного JSON и освобождение мест.

HTTP-тесты использовали отдельную базу `club_tests_*` и Redis database 1.
Из основной базы `club` данные только читались. SQL подготовки из этой инструкции
проверен в отдельной временной базе, которая затем удалена. У скрипта проверки
лимита проверен синтаксис; сам скрипт в основной базе не запускался.

## 1. Что проверено в реализации

| Требование | Где реализовано / результат |
| --- | --- |
| POST без тела | `EnrollmentsController.Cancel(long id, CancellationToken ct)`; `Idempotency-Key` не нужен |
| `200`: `id` — long, `status: cancelled`, `refundedVisits` — int | `CancelEnrollmentResponse`, `EnrollmentResultExtensions` |
| `404`: отсутствующая или чужая бронь | `GetByIdForUserWithDetailsAsync` ищет по ID брони **и** текущему пользователю |
| `409`, `reason: class-started` | `PrepareCancellationAsync`: активная бронь, занятие не отменено клубом, `StartsAt <= now` |
| Освобождение мест при любой успешной первой отмене | Статус становится `cancelled`; `GetOccupiedSeatsAsync` считает только `active` |
| Полный возврат за два часа или раньше | `EnrollmentRules.GetRefundedVisits`: `StartsAt - now >= TimeSpan.FromHours(2)` |
| Поздняя отмена до начала | `200`, места освобождены, `refundedVisits: 0`, остаток не меняется |
| Отмена занятия клубом, включая прошедшее время начала | `IsCancelled` разрешает отмену и полный возврат; отменённое занятие загружается через `IgnoreQueryFilters` |
| Посещения остаются списанными до обращения клиента | Возврат выполняется при первой отмене конкретной брони; другим клиентам отменённого занятия автоматический возврат не начисляется |
| Повтор возвращает исходный результат | Возвращается сохранённое `Enrollment.RefundedVisits`; время, остаток и версия кеша повторно не меняются |
| Очередь обрабатывается в этой же операции | `WaitlistPromotionService.PromoteAsync`: создаёт активные брони, списывает посещения ожидающих, меняет ожидание на `fulfilled` |
| Порядок живой очереди | `GetFirstWaitingAsync`: `created_at`, затем `id` |
| Атомарность отмены, возврата и продвижения очереди | Общая Serializable-транзакция; при сбое продвижения откатываются все изменения, конфликты транзакций повторяются |
| Актуальность GET после изменения | Повышается версия кеша отменяющего и каждого получившего бронь; обновляется также версия расписания |
| `429` | `[UserRateLimit]`: общий лимит 60 запросов за последние 60 секунд на пользователя, есть `Retry-After` |

Существующие тесты дополнительно проверяют `404`, `401`, `409`, `429`, повтор,
кеш карточки и расписания, несколько ожидающих и параллельные отмены разных
броней. Для случаев очереди, которые задание не уточняет, см. раздел 8.

## 3. Ранняя отмена, повтор и проверка карточки

Войдите как `user001@club.test`. Сначала вызовите `GET /enrollments/308`, чтобы
заполнить кеш. Для расписания используйте `GET /schedule` с
`from=2026-11-10T00:00:00Z`, `to=2026-11-11T00:00:00Z`, `limit=100`.

| Шаг | Ожидается | Статус брони | Посещения | Свободные места на занятии 109 |
| --- | --- | --- | --- | --- |
| До отмены | GET: `seats: 2` | active | 17 | 4 |
| POST `/enrollments/308/cancel` без тела | `200`, `refundedVisits: 2` | cancelled | 19 | 6 |
| Тот же POST ещё раз | `200`, **тот же JSON** | cancelled | 19 | 6 |

Успешный ответ содержит именно три поля:

```json
{"id":308,"status":"cancelled","refundedVisits":2}
```

После каждого POST повторите GET карточки и расписания: изменения должны быть
видны сразу. В карточке `seats` остаётся равным 2 — это размер отменённой брони,
а не число занятых ею мест после отмены. `id`, `createdAt`, занятие и срок
абонемента сохраняются. Поле `refundedVisits` проверяется в ответе отмены и БД,
а не в GET карточки.

`mySeats` в расписании — сумма всех активных броней пользователя на занятие.
При исходных данных у пользователя 001 на занятии 109 три брони по 2 места,
поэтому после отмены 308 значение меняется с 6 на 4. При других исходных числах
используйте формулы: посещения `до + seats`, свободные места `до + seats`,
если очередь отсутствует. Брони 306 и 307 остаются активными.

### Граница ровно двух часов

Правило включительное: `02:00:00` → полный возврат, `01:59:59` → 0.
Точная граница и значения на один тик раньше/позже проверены автоматическим
тестом `CancelAsync_AtTwoHourBoundary_RefundsInclusively`: используется тот же
момент `now`, который сервис применяет к отмене.

Через Swagger нельзя надёжно попасть в точную границу: после задания времени
начала запрос ещё идёт до сервера. Для ручных проверок по обе стороны создайте
отдельные наборы, заменив у `early` в копии SQL `interval '4 hours'` на
`interval '121 minutes'` и `interval '119 minutes'`; первый запрос отправьте
в течение минуты. Ожидаются соответственно 2 и 0. Не считайте установку
`now() + interval '2 hours'` доказательством ошибки, если пришёл нулевой возврат.

## 5. Отмена клубом и отсутствие автоматического возврата

Можно использовать `club-future` и `club-past` из подготовки либо готовые брони:

| Владелец | POST без тела | Ожидается | Остаток до → после |
| --- | --- | --- | --- |
| `user133@club.test` | `/enrollments/126/cancel` | `200`, `refundedVisits: 3` | 32 → 35 |
| `user116@club.test` | `/enrollments/220/cancel` | `200`, `refundedVisits: 2`, несмотря на прошедшее начало | 26 → 28 |

**До первого POST** откройте карточку: `class.isCancelled: true`, но бронь ещё
`active` и посещения не возвращены. После POST возвращаются только посещения
этой брони, места освобождаются. Для готовых примеров свободных мест станет
соответственно 27 и 19. Повтор возвращает тот же JSON без нового возврата.

Отмена занятия не должна сама менять статусы броней или остатки остальных
клиентов. Это дополнительно проверяет HTTP-тест
`Cancel_WhenClubCancels_RefundsOnlyEnrollmentRequestedByClient`.
В текущем API нет отдельного эндпоинта отмены занятия клубом; состояния для
ручной проверки готовятся SQL. Фонового возврата ожидать не нужно.

## 6. Отказы и отсутствие доступа

| Действие | Ожидается |
| --- | --- |
| Владелец `user003@club.test`, POST `/enrollments/233/cancel` | `409`, `reason: class-started` |
| Владелец строки `started`, POST её `enrollment_id` | `409`, `reason: class-started` |
| `user002@club.test`, POST `/enrollments/308/cancel` | `404`, чужая бронь, в том числе после её отмены владельцем |
| Авторизованный пользователь, POST `/enrollments/9223372036854775807/cancel` | `404`, такой брони нет |
| Убрать токен и отправить корректный запрос | `401`, дополнительная проверка авторизации |
| POST `/enrollments/abc/cancel` | `400`, некорректный формат ID |
| POST `/enrollments/9223372036854775808/cancel` | `400`, выход за диапазон long |

Все запросы отправляйте без тела. Для проверки `404` у начавшейся чужой брони
вызовите `/enrollments/233/cancel` под `user002@club.test`: ожидается именно
`404`, а не `class-started`. При исчерпанном лимите сначала дождитесь его
восстановления, иначе вместо этих результатов будет `429`.

`reason` находится **в корне** JSON:

```json
{"title":"Class has already started","status":409,"reason":"class-started"}
```

Могут присутствовать стандартные поля ProblemDetails. У `404` поле `reason`
не требуется. После любого отказа проверяйте неизменность статуса, мест,
`cancelled_at`, `refunded_visits`, остатка абонемента и очереди. При `409`
бронь остаётся активной. В точный момент начала неотменённого занятия первая
отмена уже запрещена; это также проверено тестом подготовки с `StartsAt == now`.

## 7. Повтор после начала занятия и изменения его состояния

1. Под `user169@club.test` дважды вызовите `/enrollments/231/cancel`.
   Ожидается `200` и `{"id":231,"status":"cancelled","refundedVisits":2}`.
   Хотя начало прошло, отказа `class-started` нет; остаток остаётся 11.
2. После успешной поздней отмены строки `late` сохраните ответ с возвратом 0.
   Когда начало пройдёт, повторите запрос: по-прежнему `200` и возврат 0.
3. Если клуб отменит занятие **после того, как клиент уже отменил свою бронь
   без возврата**, повтор сохраняет первоначальный возврат 0. Нового начисления
   не происходит. Такой случай покрыт HTTP-тестом повтора после изменения занятия.

Для ускоренной проверки пункта 3 на **собственной строке `late` из подготовки**
после первой отмены подставьте её ID занятия:

```powershell
$classId = 0 # замените на class_id своей строки late
if ($classId -le 0) { throw 'Укажите class_id тестового занятия late' }
@'
UPDATE classes SET is_cancelled = true, starts_at = now() - interval '1 minute'
WHERE id = :class_id AND title = 'Manual cancel: late';
'@ | docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -v "class_id=$classId" -U club -d club
```

Ожидается `UPDATE 1`. Затем повторите POST этой брони: `200`, возврат 0, остаток
5, время отмены прежнее. SQL меняет занятие напрямую и не обновляет кеш GET;
для этого шага сверяйте POST и БД. Изменения, сделанные через сам эндпоинт
отмены, обновляют кеш штатно.

## 8. Освободившиеся места и очередь ожидания

Используйте строки `fifo` из подготовки. У одного `owner` две активные брони:
строка `owner` — 3 места, `owner-2` — 2 места. Вместимость 5, свободных мест 0.
У owner и каждого A, B, C исходно по 5 оставшихся посещений.

### Постановка в очередь

Последовательно входите под A, B, C и вызывайте `POST /enrollments/waitlist`.
Здесь тело и заголовок `Idempotency-Key` нужны: это отдельный эндпоинт постановки.
Подставляйте общий `class_id` набора `fifo`, а не ID брони.

| Пользователь | Тело (CLASS_ID замените числом) | Уникальный ключ | Ожидается |
| --- | --- | --- | --- |
| A | `{"classId":CLASS_ID,"seats":1}` | `manual-cancel-A-<новый суффикс>` | `201`, `position: 1` |
| B | `{"classId":CLASS_ID,"seats":2}` | `manual-cancel-B-<новый суффикс>` | `201`, `position: 2` |
| C | `{"classId":CLASS_ID,"seats":1}` | `manual-cancel-C-<новый суффикс>` | `201`, `position: 3` |

Сохраните ID ожиданий из ответов. До отмены у всех `waiting`, новых активных
броней у A/B/C нет и посещения всё ещё 5. При повторении постановки используйте
новые ключи для новых сценариев; повтор старого ключа возвращает старый ответ.

### Отмена с немедленным продвижением

Войдите под owner. Выполняйте POST без тела:

| Шаг | Результат отмены | Очередь и новые брони сразу после ответа | Посещения owner / A / B / C | Свободно |
| --- | --- | --- | --- | --- |
| Отменить бронь `owner` на 3 места | `200`, возврат 3 | A и B — `fulfilled`, создано по одной активной брони на 1 и 2 места; C — `waiting` | 8 / 4 / 3 / 5 | 0 |
| Повторить её отмену | Тот же `200`, возврат 3 | Всё без изменений, новых броней нет | 8 / 4 / 3 / 5 | 0 |
| Отменить бронь `owner-2` на 2 места | `200`, возврат 2 | C — `fulfilled`, создана активная бронь на 1 место | 10 / 4 / 3 / 4 | 1 |
| Повторить вторую отмену | Тот же `200`, возврат 2 | Без изменений | 10 / 4 / 3 / 4 | 1 |

Вызовов подтверждения от A/B/C и ожидания фоновой обработки нет. ID новых
броней найдите SQL из раздела 11 и откройте GET под соответствующим владельцем.
Запись ожидания и новая бронь имеют разные ID. POST отмены возвращает только
результат отменяемой брони; сведения о продвижении в его JSON не добавляются.

Нулевые `freeSeats` после первого шага **не означают, что места не освобождены**:
они сразу переданы A и B. Проверяйте статус исходной брони и сумму мест новых
активных броней. В расписании меняются также `mySeats` владельца и ожидающих.
Откройте расписание до и после операции, указав интервал вокруг `starts_at_utc`
из таблицы подготовки, `roomId` из карточки владельца и `limit=100`.

Повторите те же шаги для независимого набора `fifo-late` до начала его занятия.
Продвижение и списания у A/B/C должны быть теми же, но оба возврата owner равны
**0**, а его остаток всё время остаётся **5**. Это проверяет освобождение и
передачу мест даже при поздней отмене без возврата.

### Решения для условий, не уточнённых в задании

Текущая реализация использует строгую очередь и целое число мест каждой заявки:

- Если первому не хватает свободных мест на всю заявку, очередь останавливается;
  более поздние заявки его не обходят. Частичного продвижения нет.
- Если у первого просрочен абонемент или не хватает посещений, он остаётся
  первым в ожидании, остальные также ждут.
- На занятие, отменённое клубом, новые активные брони из ожидания не создаются;
  клиенту возвращаются посещения и освобождаются места, ожидания сохраняются.

Это принятые в коде решения, а не дополнительные требования из формулировки
пункта 3. Первые два могут оставить свободные места при наличии ожидающих.
Они покрыты существующими HTTP-тестами. Для ручной проверки нехватки мест
создайте новый набор `fifo`, поставьте A на **4** места, B на **1** и отмените
бронь owner на 3 места: оба останутся `waiting`, свободных мест будет 3.
После отмены оставшихся 2 мест A и B получат брони в этом порядке.

## 9. Ограничение частоты — проверять последним

Лимит общий для всех восьми эндпоинтов задания: 60 запросов за последние
60 секунд на одного пользователя. GET, ошибки и повторы отмены тоже расходуют
лимит. Новый токен этого же пользователя его не сбрасывает.

Скрипт [Test-EnrollmentCancellationRateLimit.ps1](Test-EnrollmentCancellationRateLimit.ps1)
принимает **только уже отменённую бронь**: сначала проверяет это через GET.
Для готовой брони 231:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Docs\Test-EnrollmentCancellationRateLimit.ps1 -EnrollmentId 231 -Email user169@club.test
```

Можно передать ID и email уже отменённой строки `early` из своего набора.
Скрипт входит, читает карточку и сохранённый результат отмены, ждёт 61 секунду,
затем отправляет 61 POST без тела менее чем за минуту. Первые 60 должны вернуть
`200` с одинаковым JSON, запрос 61 — `429` с `Retry-After` от 1 до 60 секунд.
После ожидания проверяются восстановление `200` и неизменность карточки,
включая остаток посещений. При несовпадении скрипт завершается с ошибкой.

Не выполняйте другие запросы задания от того же пользователя во время прогона
и не меняйте его бронь или абонемент. Если начальный GET уже вернул `429`,
подождите 61 секунду и запустите заново. В HTTP-тестах также проверено, что
отмена **активной** брони, отклонённая лимитом, не меняет её статус и посещения.

## 11. Как сверить базу и очередь

Запросы ниже только читают данные. Выполняйте их до и после операции.
Не меняйте те же брони и абонементы параллельно с проверкой.

### Бронь, посещения и свободные места

```powershell
$enrollmentId = 308 # замените на проверяемый enrollment_id
@'
SELECT e.id AS enrollment_id, u.email, e.class_id, e.seats, e.status,
       e.cancelled_at, e.refunded_visits, c.starts_at, c.is_cancelled,
       p.remaining_visits, p.valid_until,
       c.capacity - COALESCE((
           SELECT SUM(a.seats) FROM enrollments a
           WHERE a.class_id = e.class_id AND a.status = 'active'
       ), 0) AS free_seats
FROM enrollments e
JOIN users u ON u.id = e.user_id
JOIN classes c ON c.id = e.class_id
JOIN passes p ON p.user_id = e.user_id
WHERE e.id = :enrollment_id;
'@ | docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -v "enrollment_id=$enrollmentId" -U club -d club
```

Время PostgreSQL здесь выводится в UTC; Минск — UTC+3. При повторе сохраняются
в том числе `cancelled_at` и `refunded_visits`. При первой отмене без очереди
`free_seats` увеличивается на `seats` даже при нулевом возврате.

### Ожидания, активные брони и остатки всех участников занятия

```powershell
$classId = 0 # замените на class_id своего fifo или fifo-late
if ($classId -le 0) { throw 'Укажите class_id тестового занятия' }
@'
SELECT w.id AS waitlist_id, u.email, w.seats, w.status, w.created_at,
       p.remaining_visits
FROM waitlist_entries w
JOIN users u ON u.id = w.user_id
JOIN passes p ON p.user_id = w.user_id
WHERE w.class_id = :class_id
ORDER BY w.created_at, w.id;

SELECT e.id AS enrollment_id, u.email, e.seats, e.status,
       e.cancelled_at, e.refunded_visits, p.remaining_visits
FROM enrollments e
JOIN users u ON u.id = e.user_id
JOIN passes p ON p.user_id = e.user_id
WHERE e.class_id = :class_id
ORDER BY e.id;
'@ | docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -v "class_id=$classId" -U club -d club
```

Сразу после успешного POST сверяйте таблицу из раздела 8. Повтор не создаёт
дубликаты броней и не списывает посещения повторно. При отказах и повторе
состав очереди, число броней и остатки не меняются.
