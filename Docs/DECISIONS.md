# Решения и ограничения

Ниже описаны выбранные варианты поведения и технические решения. Соответствующие места
в коде отмечены комментариями `// решение:`.

1. **Заявки из очереди выдаются целиком.** Если первой заявке не хватает свободных мест,
   обработка останавливается. Частичная выдача и обход первой заявки следующими не выполняются.
   Это сохраняет порядок ожидания и позволяет клиенту получить все места для своей группы.
   Следствие: свободные места могут оставаться при наличии ожидающих.

2. **Проблема с абонементом первого клиента останавливает очередь.** При просроченном
   абонементе или нехватке посещений первая заявка сохраняет статус `waiting` и свою позицию.
   Клиента не удаляем и не пропускаем, чтобы сохранить его место в очереди. Проверка абонемента
   выполняется при попытке выдать места; постановка в очередь посещений не списывает и
   не резервирует. Это позволяет ждать до пополнения или продления абонемента, но само
   изменение абонемента обработку очереди не запускает.

3. **Выход из очереди после выдачи места сохраняет бронь.** Даже если заявка уже имеет статус
   `fulfilled`, её отмена возвращает `200` и переводит только заявку в `cancelled`.
   Созданная бронь остаётся активной, посещения не возвращаются. Для неё предусмотрен
   отдельный эндпоинт отмены с собственными правилами возврата.

4. **При одинаковом времени постановки сравниваются идентификаторы.** Очередь упорядочена
   по `createdAt`, затем по `id`. Тот же порядок используется для расчёта позиции.
   Это делает выдачу мест и нумерацию однозначными при совпадении временных меток.

5. **Ключ идемпотентности ограничен пользователем и операцией.** Одинаковые ключи разных
   пользователей независимы. Один пользователь может использовать одинаковый ключ для
   создания брони и постановки в очередь: это разные операции. Так запросы к разным
   эндпоинтам не конфликтуют между собой.

   В базе хранится полный ключ без ограничения длины; для поиска индексируется его SHA-256.
   После поиска сравнивается и исходный ключ, поэтому совпадение хешей не объединяет запросы.

6. **Повтор ключа с другими параметрами отклоняется.** Если у того же пользователя в той же
   операции ключ уже использован с другим `classId` или `seats`, возвращается `409` с
   дополнительной причиной **`idempotency-key-reused`** в верхнеуровневом поле `reason`
   ответа ProblemDetails. Это исключает использование одного ключа для разных действий.

   При совпадении параметров возвращается сохранённый успешный ответ без нового списания
   или постановки в очередь. Для очереди сохраняется и первоначальное значение `position`:
   повтор ключа воспроизводит первый ответ, а не пересчитывает текущую позицию. После выхода
   из очереди повтор старого ключа не создаёт новую заявку; для новой операции нужен новый ключ.

7. **Время создания усекается до микросекунд.** Это соответствует точности PostgreSQL
   и сохраняет одинаковое значение `createdAt` в первоначальном ответе и после чтения из базы.
   Правило применяется к броням, заявкам ожидания и броням, созданным при выдаче мест из очереди.

8. **Карточки используют общую версию кэша для каждого пользователя.** Версия входит в ключ
   карточки и изменяется в той же транзакции, что бронь и абонемент, включая автоматическую
   выдачу места из очереди. Поэтому изменение остатка посещений делает неактуальным кэш всех
   карточек пользователя. Запоздалая запись старого ответа остаётся под старой версией ключа.
   Новый пользователь до первого изменения имеет версию 0. Миграция заполняет версии
   существующих пользователей нулями; префикс `v2` исключает чтение прежних ключей Redis.

   Расписание и аналитика используют сумму пользовательских версий и отдельной версии
   расписания. Триггеры PostgreSQL обновляют версию расписания в той же транзакции при вставке,
   изменении, удалении или очистке занятий и залов, включая прямые SQL-запросы. Откат транзакции
   откатывает и версию. Операции бронирования изменяют только пользовательские версии и
   не блокируют общую строку расписания. Все версии читаются одним SQL-запросом; префикс `v3`
   исключает чтение старых записей кэша расписания и аналитики. Цена этого решения — чтение
   таблицы версий пользователей для определения ключа кэша общих выборок.

9. **Изменения выполняются в транзакциях Serializable с повтором при конфликте.** Это
   согласует конкурентные проверки свободных мест и посещений. Отмена брони, возврат посещений
   и выдача мест ожидающим входят в одну транзакцию, чтобы ошибка не оставляла частичных изменений.
   При конфликте сериализации или взаимной блокировке повторяется вся операция с очисткой
   отслеживаемых сущностей. Повторяется также конфликт уникальности ожидающей заявки,
   возникший при конкурентной постановке в очередь.

   Число попыток ограничено 12, чтобы запрос не повторялся бесконечно. Задержка растёт
   экспоненциально от 10–20 мс до 500–1000 мс со случайным разбросом, уменьшающим повторные
   столкновения запросов. Отмена запроса прерывает ожидание. Постоянные ошибки не повторяются.

10. **Токен продолжения — JSON с версией формата в Base64Url.** Он хранит границы периода,
    фильтр зала и последнюю пару `(startsAt, classId)`. Это позволяет передавать состояние
    страницы одним параметром URL. Следующая страница выбирается после последней пары,
    без OFFSET. Токен проверяется на соответствие периоду и залу текущего запроса.

    Границы периода сохраняют точность входных дат, в том числе семь дробных знаков.
    В запросе к PostgreSQL границы усекаются до микросекунд: для нецелой микросекунды сравнение
    `>= from` заменяется на `> усечённый from`, а `< to` — на `<= усечённый to`. Это сохраняет
    интервал `[from, to)` без переполнения на максимальной дате. Токен хранит исходные границы.

11. **Расписание использует частичные составные индексы.** Индексы `(starts_at, id)` и
    `(room_id, starts_at, id)` содержат только занятия с `NOT is_cancelled`, как и запросы
    расписания. Они позволяют искать страницу по периоду и залу в нужном порядке без чтения
    всей истории занятий. Полный индекс по `room_id` сохранён для запросов, включающих
    отменённые занятия. Индексы добавляются отдельной миграцией без изменения данных.

Ограничения и то, что осталось за рамками:

- Продвижение очереди запускается при первой успешной отмене активной брони. Уменьшение
  числа мест, выход из очереди, повторная отмена и изменение абонемента его не запускают.
  Фоновый пересмотр очереди не реализован: обработка ограничена сценарием отмены брони,
  для которого она явно требуется заданием.
- Порядок ожидания соблюдается при автоматической выдаче мест. Обычное создание брони
  проверяет доступные места и абонемент, но не резервирует свободные места за очередью
  и не добавляет отказ из-за наличия ожидающих.
- При отмене занятия клубом или после его начала новые брони из очереди не создаются.
  Ожидающие заявки сохраняются; автоматическая очистка и уведомления не реализованы.
- Автоматическая очистка сохранённых результатов идемпотентности не реализована,
  поскольку срок действия ключа контрактом не ограничен.
- При дальнейшем росте числа пользователей можно перейти на версии кэша по залу и дате
  занятия. Дальнейшая оптимизация под реальной конкурентной нагрузкой остаётся отдельной
  доработкой; проверка плана SQL на большом наборе данных не заменяет нагрузочный тест сервиса.
