## 1. Что проверено в реализации

| Требование | Где реализовано / результат |
| --- | --- |
| POST с итоговым числом мест | `EnrollmentsController.ChangeSeats`, `ChangeEnrollmentSeatsRequest`; `seats` — новое значение, не разница |
| `400`: поле обязательно, целое, не меньше 1 | Nullable `int?`, `[Required]`, `[Range(1, int.MaxValue)]`, привязка JSON и `[ApiController]` |
| `404`: отсутствующая или чужая бронь | `GetByIdForUserWithDetailsAsync` ищет одновременно по ID брони и текущему пользователю |
| Запрет изменения отменённой брони, отменённого или начавшегося занятия | `PrepareSeatChangeAsync`, `EnrollmentRules`; проверки выполняются до вычисления допустимости увеличения |
| Увеличение требует посещений и свободных мест | Проверяется `delta = новое число − текущее число`, а не всё новое число; занятые места считаются по всем активным броням |
| Уменьшение возвращает разницу даже при просроченном или пустом абонементе | При `delta <= 0` проверки срока, остатка посещений и свободных мест пропускаются |
| То же число мест | Состояние брони и занятия проверяется; при успехе `200`, сохранение и изменение версии кеша не выполняются |
| Списание / возврат | `SaveSeatChangeAsync`: меняет `enrollment.Seats`, вычитает `delta` из `pass.RemainingVisits` |
| Полная карточка при `200` | Тот же `EnrollmentDetailsResponse` и маппинг, что у GET карточки; загружаются `Class` и `Class.Room`, добавляется `Pass` |
| Все шесть причин `409` | `EnrollmentResultExtensions`: `capacity-exceeded`, `pass-exhausted`, `pass-expired`, `class-started`, `class-cancelled`, `enrollment-cancelled` |
| `429` | `[UserRateLimit]` на контроллере, общий лимит 60 запросов за последние 60 секунд на пользователя; ответ содержит `Retry-After` |
| Атомарность и актуальность карточки | Изменение выполняется в Serializable-транзакции с повторами конфликтов; после изменения повышается версия кеша карточек и расписания |

Существующие тесты проверяют увеличение и уменьшение с сохранением остатка,
полную вложенную модель, валидацию, чужую и отсутствующую бронь, все причины
отказа, возврат при одновременно просроченном и пустом абонементе, повтор без
изменения мест и обновление GET после изменения. Ограничение частоты проверяется
HTTP-тестами в том числе для `/seats` и для отклонённого изменения данных.

## 3. Увеличение, повтор и уменьшение

Войдите как `user001@club.test`. Сначала откройте `GET /enrollments/306`, чтобы
прочитать карточку и заполнить её кеш. При исходных числах из таблицы:

| Шаг | POST `/enrollments/306/seats`, тело | Ожидается | seats в карточке | pass.remainingVisits | Свободных мест на занятии 109 |
| --- | --- | --- | --- | --- | --- |
| 1 | `{"seats":4}` | `200`, списана только разница 2 | 4 | 15 | 2 |
| 2 | `{"seats":4}` | `200`, ничего не изменилось | 4 | 15 | 2 |
| 3 | `{"seats":1}` | `200`, возвращена разница 3 | 1 | 18 | 5 |
| 4 | `{"seats":2}` | `200`, исходное состояние восстановлено | 2 | 17 | 4 |

После каждого шага повторяйте GET: он должен сразу возвращать новые значения,
включая остаток абонемента. `id`, `status` и `createdAt` брони сохраняются.
При других исходных остатках считайте относительно них:
`остаток после = остаток до − (новые места − старые места)`.

Проверьте, что **сам ответ POST**, без дополнительного GET, содержит полную
карточку. Например, после первого шага структура будет такой
(`createdAt` условный, остальные числа соответствуют таблице):

```json
{
  "id": 306,
  "status": "active",
  "seats": 4,
  "createdAt": "2026-11-08T08:30:00Z",
  "class": {
    "id": 109,
    "title": "TRX",
    "startsAt": "2026-11-10T17:47:00Z",
    "durationMinutes": 45,
    "isCancelled": false,
    "room": {"id": 9, "name": "Hall J"}
  },
  "pass": {"remainingVisits": 15, "validUntil": "2027-03-02"}
}
```

`durationMinutes` сверяйте с исходным GET; значение в примере иллюстративное.
Поле `classId` из краткого ответа создания здесь заменено вложенным `class`.
После POST содержимое полной карточки должно совпадать с GET этой же брони.

В `GET /schedule` укажите `from=2026-11-10T00:00:00Z`,
`to=2026-11-11T00:00:00Z`, `limit=100`. У занятия 109 сверяйте `freeSeats`
по таблице выше. `mySeats` — сумма **всех** активных броней пользователя на занятие:
сейчас у пользователя 001 там три брони по 2 места (306, 307, 308), поэтому
`mySeats` исходно 6, по шагам — 8, 8, 5, 6. В самой карточке `seats` относится
только к изменяемой брони.

## 5. Все шесть причин 409, в том числе при том же числе мест

До изменяющих сценариев следующих разделов выполните:

| Пользователь | ID брони | Тело | reason |
| --- | --- | --- | --- |
| `user023@club.test` | `255` | `{"seats":4}` | `capacity-exceeded`: свободно 1, нужно добавить 2 |
| `user110@club.test` | `118` | `{"seats":2}` | `pass-exhausted`: осталось 0, нужно добавить 1 |
| `user017@club.test` | `186` | `{"seats":3}` | `pass-expired` |
| `user001@club.test` | `111` | По очереди `{"seats":1}`, `{"seats":3}`, `{"seats":4}` | `class-started` во всех трёх случаях |
| `user133@club.test` | `126` | По очереди `{"seats":1}`, `{"seats":3}`, `{"seats":4}` | `class-cancelled` во всех трёх случаях |
| `user076@club.test` | `9` | По очереди `{"seats":1}`, `{"seats":3}`, `{"seats":4}` | `enrollment-cancelled` во всех трёх случаях |

Повторная проверка 08.11.2026: все 12 запросов из этой таблицы выполнены через
работающий локальный API и вернули ожидаемые `409` и `reason`. Состояние шести
броней, занятий и абонементов до и после запросов совпало. В первоначальной
версии инструкции для брони 126 ошибочно был указан пользователь 127;
правильный владелец — пользователь 133. Дополнительный запрос под пользователем
127 подтвердил `404` для этой чужой брони.

Три запроса для каждого недоступного состояния проверяют уменьшение, то же
количество и увеличение. Все они должны вернуть `409`, а не `200`.
`reason` находится **в корне** JSON:

```json
{"title":"Class has already started","status":409,"reason":"class-started"}
```

В реальном ответе могут также присутствовать стандартные поля ProblemDetails.
При отказе проверьте неизменность брони и остатка абонемента через GET владельца.
Если одновременно нарушено несколько условий, код сначала проверяет бронь,
потом занятие, затем при увеличении абонемент и вместимость. Поэтому, например,
для отменённой брони на начавшееся занятие вернётся `enrollment-cancelled`.
В задании отдельный приоритет причин не установлен.

Чтобы самостоятельно убедиться, что бронь на отменённое занятие можно отменить,
**после** всех проверок `/126/seats` выполните под пользователем 133
`POST /enrollments/126/cancel` без тела: ожидается `200`, `status: cancelled`,
`refundedVisits: 3`. После этого `/126/seats` будет возвращать уже
`enrollment-cancelled`. Этот шаг меняет исходные данные для повторного прогона.

## 7. Просроченный и исчерпанный абонемент

### Просроченный: уменьшение разрешено, увеличение запрещено

Войдите как `user017@club.test`. Для брони `186` исходно `seats: 2`,
`pass.remainingVisits: 25`, `pass.validUntil: 2026-10-15`:

1. `{"seats":3}` → `409`, `pass-expired`, остаток 25.
2. `{"seats":2}` → `200`, по-прежнему 2 места и 25 посещений.
3. `{"seats":1}` → `200`, 1 место и 26 посещений; освобождено одно место.
4. `{"seats":1}` → `200`, по-прежнему 1 место и 26 посещений.
5. `{"seats":2}` → `409`, `pass-expired`, хотя посещений уже 26.

Срок абонемента остаётся прежним. Через этот эндпоинт вернуть бронь к двум местам
при просроченном абонементе нельзя; для повторения используйте другую бронь
с двумя или более местами либо данные из раздела 8.

### Исчерпанный: проверяется только разница, уменьшение возвращает посещения

## 8. Одновременно просроченный и пустой абонемент — отдельные данные

Этот случай покрыт автоматическими тестами. Для ручной проверки можно создать
отдельного пользователя и его бронь в локальной учебной базе: через обычный POST
создания невозможно завести новую бронь на уже просроченный и пустой абонемент.

Следующий блок **создаёт** одного нового пользователя, абонемент, занятие и бронь,
не меняя существующие записи. Он копирует только тестовый хеш пароля пользователя
001, поэтому пароль нового пользователя тоже `Password123!`. Запускайте его из
корня проекта. При каждом запуске создаётся новый набор, ID и email печатаются
в конце. Даты считаются от текущего времени.

```powershell
@'
BEGIN;
WITH new_user AS (
    INSERT INTO users (email, password_hash, role, created_at)
    SELECT 'manual-seats-' || gen_random_uuid()::text || '@club.test',
           password_hash, 'user', now()
    FROM users WHERE email = 'user001@club.test'
    RETURNING id, email
), new_pass AS (
    INSERT INTO passes (user_id, remaining_visits, valid_until)
    SELECT id, 0, (now() AT TIME ZONE 'UTC')::date - 1 FROM new_user
    RETURNING user_id
), new_class AS (
    INSERT INTO classes (room_id, title, starts_at, duration_minutes, capacity, is_cancelled)
    SELECT id, 'Manual seats: expired and empty', now() + interval '7 days', 60, 10, false
    FROM rooms ORDER BY id LIMIT 1
    RETURNING id
), new_enrollment AS (
    INSERT INTO enrollments (user_id, class_id, seats, status, created_at)
    SELECT p.user_id, c.id, 3, 'active', now() FROM new_pass p CROSS JOIN new_class c
    RETURNING id, user_id, class_id
)
SELECT u.email, e.id AS enrollment_id, e.class_id
FROM new_enrollment e JOIN new_user u ON u.id = e.user_id;
COMMIT;
'@ | docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U club -d club
```

Войдите под напечатанным email. Подставьте полученный `enrollment_id` в URL:

| Тело | Ожидается | Места | Посещения |
| --- | --- | --- | --- |
| `{"seats":4}` | `409`, `pass-expired` | 3 | 0 |
| `{"seats":3}` | `200`, без изменений | 3 | 0 |
| `{"seats":1}` | `200`, возвращено 2 посещения | 1 | 2 |
| `{"seats":2}` | `409`, `pass-expired`, несмотря на возвращённые посещения | 1 | 2 |

## 9. Ограничение частоты — проверять последним

Лимит общий для всех восьми эндпоинтов задания: 60 запросов за последние
60 секунд на одного пользователя. GET карточки и расписания, ошибки и повторы
с тем же числом мест тоже расходуют лимит. Новый токен того же пользователя
его не сбрасывает.

Готовый скрипт отправляет **только текущее число мест**, чтобы не списывать
посещения при проверке. Возьмите активную бронь на неотменённое занятие,
которое начнётся более чем через пять минут:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Docs\Test-EnrollmentSeatsRateLimit.ps1 -EnrollmentId 306
```

Для другого владельца:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Docs\Test-EnrollmentSeatsRateLimit.ps1 -EnrollmentId 182 -Email user162@club.test
```

Скрипт входит, читает карточку, ждёт 61 секунду (включая выход начального GET
из окна лимита), затем менее чем за минуту отправляет 61 POST `/seats`.
Проверяет первые 60 ответов `200` с неизменной полной карточкой, ответ `429`
на запрос 61, `Retry-After`, восстановление `200` после указанного ожидания
и неизменность карточки через GET. При несовпадении завершится с ошибкой.
Во время проверки не вызывайте другие эндпоинты задания от этого пользователя
и не меняйте его брони или абонемент. Новые брони скрипт не создаёт.

В рамках текущей проверки `429` подтверждён существующими HTTP-тестами;
этот новый ручной скрипт проверен синтаксически, в основной базе не запускался.

## 10. Отдельный запрос из PowerShell

Запускайте после восстановления лимита. Этот пример изменяет бронь 306
на **итоговые 4 места**. `curl.exe -i` показывает статус, заголовки и JSON.

```powershell
$login = Invoke-RestMethod -Method Post `
  -Uri 'http://localhost:5080/auth/login' `
  -ContentType 'application/json' `
  -Body '{"email":"user001@club.test","password":"Password123!"}'

'{"seats":4}' | curl.exe -i `
  -X POST 'http://localhost:5080/enrollments/306/seats' `
  -H "Authorization: Bearer $($login.accessToken)" `
  -H 'Content-Type: application/json' `
  --data-binary '@-'
```

## 11. Как сверить базу или подобрать другие примеры

Запрос только читает данные. В столбце `enrollment_id` находится ID для URL,
`class_id` нужен для расписания. Время PostgreSQL печатает в UTC; Минск — UTC+3.

```powershell
@'
SELECT e.id AS enrollment_id, u.email, e.class_id, e.seats, e.status,
       c.starts_at, c.is_cancelled, c.capacity,
       p.remaining_visits, p.valid_until,
       c.capacity - COALESCE((
           SELECT SUM(a.seats) FROM enrollments a
           WHERE a.class_id = e.class_id AND a.status = 'active'
       ), 0) AS free_seats
FROM enrollments e
JOIN users u ON u.id = e.user_id
JOIN classes c ON c.id = e.class_id
JOIN passes p ON p.user_id = e.user_id
ORDER BY u.email, e.id;
'@ | docker compose exec -T postgres psql -U club -d club
```

После каждого успешного изменения сверяйте `seats`, `remaining_visits` и
`free_seats`. После `400`, `404`, `409`, `429` они должны оставаться прежними.
При POST с тем же числом мест также ничего не меняется. Не выполняйте другие
изменяющие запросы параллельно с такой сверкой.
