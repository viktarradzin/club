## 1. Вход и подготовка в Swagger

Откройте <http://localhost:5080/swagger>.
В `POST /auth/login` нажмите **Try it out** и отправьте:

```json
{
  "email": "user001@club.test",
  "password": "Password123!"
}
```

Скопируйте `accessToken` из ответа. Нажмите **Authorize**, вставьте сам токен
без префикса `Bearer`, затем **Authorize** и **Close**.

Для каждого нового сценария используйте новый `Idempotency-Key`, например
`manual-success-01`, `manual-full-01`. Повторяйте старый ключ только в проверке
идемпотентности. Для повторного полного прогона замените суффикс ключей.

## 2. Успешная запись и повтор запроса

В `POST /enrollments` задайте заголовок `Idempotency-Key: manual-success-01`:

```json
{"classId":109,"seats":2}
```

Ожидается `201` и ровно следующие поля:

```json
{
  "id": 123,
  "classId": 109,
  "seats": 2,
  "status": "active",
  "createdAt": "2026-11-08T07:30:00Z"
}
```

`id` и `createdAt` в примере условные. Сохраните настоящий `id`.

В `GET /enrollments/{id}` проверьте `seats: 2`, `status: active`,
`pass.remainingVisits: 21` — списано ровно 2 посещения.

В `GET /schedule` задайте `from=2026-11-08T00:00:00Z`,
`to=2026-11-15T00:00:00Z`, `limit=100`. У занятия 109 должно быть
`freeSeats: 8`, `mySeats: 2`.

Повторите исходный POST с тем же ключом и тем же телом. Ожидается снова `201`,
полностью тот же ответ, включая `id` и `createdAt`. Посещений по-прежнему 21,
свободных мест по-прежнему 8.

С тем же ключом отправьте `{"classId":109,"seats":3}`.
Ожидается `409`, `reason: "idempotency-key-reused"`, без нового списания.
Это дополнительная причина отказа, реализованная сверх пяти причин из пункта 1.

## 3. Ошибки запроса

Войдите как `user001@club.test`. Для каждого запроса задайте новый ключ,
кроме случая проверки отсутствующего заголовка.

| Тело / изменение | Ожидается |
| --- | --- |
| `{"classId":109,"seats":0}` | `400` |
| `{"classId":109,"seats":-1}` | `400` |
| `{"classId":109}` | `400` |
| `{"seats":1}` | `400` |
| `{"classId":null,"seats":1}` | `400` |
| `{"classId":109,"seats":null}` | `400` |
| `{"classId":"abc","seats":1}` | `400` |
| `{"classId":109,"seats":1.5}` | `400` |
| `{"classId":109,"seats":2147483648}` | `400`, выход за диапазон int |
| `{"classId":9223372036854775808,"seats":1}` | `400`, выход за диапазон long |
| Корректное тело, заголовок `Idempotency-Key` удалён | `400` |
| `{"classId":9223372036854775807,"seats":1}` | `404` |

В Swagger обязательный заголовок может проверяться интерфейсом до отправки.
Чтобы проверить ответ сервера без заголовка, используйте Postman либо запрос
PowerShell из раздела 6, удалив строку с `Idempotency-Key`.

## 4. Все пять причин 409

При смене пользователя выполните вход и замените токен в **Authorize**.
У всех пользователей пароль `Password123!`. Для каждого запроса нужен новый ключ.

| Пользователь | Тело | Ожидаемый reason при 409 |
| --- | --- | --- |
| `user001@club.test` | `{"classId":103,"seats":1}` | `capacity-exceeded` |
| `user001@club.test` | `{"classId":104,"seats":2}` | `capacity-exceeded`, есть одно место, но запрошено два |
| `user010@club.test` | `{"classId":109,"seats":2}` | `pass-exhausted`, есть одно посещение, но запрошено два |
| `user020@club.test` | `{"classId":109,"seats":1}` | `pass-exhausted` |
| `user017@club.test` | `{"classId":109,"seats":1}` | `pass-expired` |
| `user001@club.test` | `{"classId":2,"seats":1}` | `class-started` |
| `user001@club.test` | `{"classId":105,"seats":1}` | `class-cancelled` |

Поле `reason` находится в корне JSON ответа. При отказах остатки посещений и мест
не меняются. При нехватке мест запись в лист ожидания не создаётся.

Чтобы проверить границу вместимости, после отказа для занятия 104 отправьте
`{"classId":104,"seats":1}` под пользователем 001 с новым ключом: ожидается `201`.
Ещё один запрос на это занятие с новым ключом должен вернуть `capacity-exceeded`.

Для проверки отсутствия записи в очередь и подсчёта активных мест можно выполнить
следующие команды в терминале из каталога проекта:

```powershell
docker compose exec -T postgres psql -U club -d club -c "SELECT COUNT(*) FROM waitlist_entries;"
docker compose exec -T postgres psql -U club -d club -c "SELECT class_id, SUM(seats) FROM enrollments WHERE status = 'active' AND class_id IN (103,104,109) GROUP BY class_id;"
```

Если вы не вызывали отдельный эндпоинт очереди, количество записей в очереди
должно остаться 0. Места всех пользователей и всех активных броней суммируются;
отменённые брони в сумму не входят.

## 5. Ограничение частоты — проверять последним

Лимит составляет 60 запросов за последние 60 секунд на одного пользователя.
Он общий для `/enrollments`, `/schedule`, `/analytics/load` и операций очереди.
Ошибочные запросы и идемпотентные повторы также расходуют лимит.

Отправьте более 60 одинаковых POST за минуту, используя ключ и тело уже успешной
записи. Сначала будут ответы `201` с исходной бронью, после исчерпания лимита —
`429` и заголовок `Retry-After`. Дождитесь указанного числа секунд и повторите.
Новые брони и дополнительные списания при таком повторе не создаются.

Готовый PowerShell-скрипт для проверки только `POST /enrollments`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Docs\Test-EnrollmentRateLimit.ps1
```

По умолчанию используются `user001@club.test`, занятие 109, два места и ключ
`manual-success-01`. Если этот ключ уже использовался с тем же телом, скрипт
повторяет существующую бронь. Новый ключ создаёт одну бронь и один раз списывает
два посещения. Для другого доступного занятия и нового ключа задайте параметры:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Docs\Test-EnrollmentRateLimit.ps1 -ClassId 109 -Seats 2 -IdempotencyKey rate-check-001
```

Скрипт ждёт 61 секунду перед проверкой, затем проверяет 60 ответов `201` с одной
и той же бронью, ответ `429` на запрос 61, заголовок `Retry-After` и повторный
успешный ответ после ожидания. Не отправляйте другие запросы к восьми эндпоинтам
задания от этого пользователя во время проверки. При несовпадении ожиданий
скрипт завершается с ошибкой. `-InitialWaitSeconds 0` позволяет пропустить
начальное ожидание, если пользователь точно не выполнял запросов последнюю минуту.

## 6. Запрос из PowerShell

Этот пример создаёт бронь на одно место. Для каждого нового сценария меняйте
тело и ключ. `curl.exe -i` показывает и статус, и заголовки, и JSON ответа.

```powershell
$login = Invoke-RestMethod -Method Post `
  -Uri 'http://localhost:5080/auth/login' `
  -ContentType 'application/json' `
  -Body '{"email":"user001@club.test","password":"Password123!"}'

'{"classId":109,"seats":1}' | curl.exe -i `
  -X POST 'http://localhost:5080/enrollments' `
  -H "Authorization: Bearer $($login.accessToken)" `
  -H 'Content-Type: application/json' `
  -H 'Idempotency-Key: manual-powershell-01' `
  --data-binary '@-'
```

После этого примера значения из раздела 2 изменятся ещё на одно место и посещение.
